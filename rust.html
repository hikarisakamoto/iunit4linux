0Orientation

Rust has a reputation for being hard to start. Most of that reputation comes from features this project does not use. Here is what you can ignore.

What you are allowed to skip

This matters more than it sounds. Beginners stall because they try to learn Rust front-to-back before writing anything. You will not need any of the following, at any point, and you can close every browser tab about them:

  • skipasync/await, futures, tokio. This program is one thread that sleeps for a second. Async would be strictly worse.
  • skipThreads, channels, Mutex, Send/Sync. None. One shared flag appears in step 8 as three lines of documented boilerplate.
  • skipLifetime annotations — the <'a> things. You will never write one here, because we return owned values everywhere. That is a legitimate permanent style, not a beginner crutch.
  • skipWriting traits, generics, trait bounds. You will use three traits from the standard library and author none.
  • skipCustom error types, thiserror, From impls. One boxed error type carries you the whole way.
  • skipunsafe, FFI, libc, bindgen. Zero. A task that sounds like it needs USB bindings needs none at all.
  • skipRc, RefCell, interior mutability, smart pointers. Not once.

If you are working through The Rust Programming Language alongside this: chapters 1–9, 11 and 13 cover everything used here. Chapter 10 (generics, traits, lifetimes), 15 (smart pointers) and 16 (concurrency) can wait.

Reading compiler errors

Rust's errors are long, and beginners bounce off them by reading top-down. Read bottom-up: the help: line at the end very often contains the literal fix. Two habits worth forming on day one:

  • cargo clippy after every step. It is a free, tireless reviewer that catches non-idiomatic code before a human would, and its suggestions are genuinely instructive.
  • rustc --explain E0502 for any error code you do not recognise — it prints a page-long explanation with examples.
Do the shell warm-up first

Before writing any Rust, go and do the warm-up on the foundations page — driving the panel with printf and dd. It takes thirty seconds. From then on, every failure is definitely in your code, and when you are new to a language that certainty is worth a lot.

1The packet builder

Turn two temperatures into the twelve bytes from the protocol table. Pure functions, no files, no device — and therefore testable before you have met anything hard.

Two functions: one that splits a single temperature into its three digit bytes, one that assembles and checksums the packet. Either half of the panel can be absent, so the digit function needs to express “no reading” and return 0xEE 0xEE 0xEE.

That is Option<f32> — Rust's answer to a nil pointer, except the compiler forces you to handle the absent case. You will handle it with match, which is a switch that must cover every possibility.

Reach for

[u8; 12] and [u8; 3] — fixed-size arrays, not Vec. const for the blank triple. f32::clamp and f32::round. copy_from_slice to drop a triple into place. {:02X?} to print an array as hex while you are poking at it.

Gotcha · the checksum overflows, and Rust panics

The big one. 0x55 + 0xAA + 0x01 = 0x100 — your accumulator exceeds a byte on the third byte of every packet, before any temperature is involved.

If you accumulate in a u8, a debug build panics with attempt to add with overflow, and a release build silently wraps — giving the correct answer, because the spec wants exactly that. So the bug presents as “my program only crashes when I'm developing, and works when I ship it”, which is backwards from every instinct you have.

Sum into a u32 and narrow once at the end with as u8. (Go, for contrast, wraps silently in every build and you never notice.)

Gotcha · as has two different behaviours

300.7_f32 as u8 gives 255 — float-to-integer casts saturate. 300_i32 as u8 gives 44 — integer-to-integer casts wrap. Same keyword, opposite rules, no warning either way.

Clamp before you cast, every time, and the distinction stops mattering.

Reaching for the wrong tool

Do not build this as a String. Two independent reasons: the digits are values, not characters (44.3 °C is 0x04, not b'4'), and Rust's String is validated UTF-8, so 0xEE cannot legally go in one at all. The compiler will stop you, but it is worth knowing why.

Checkpoint

Write tests. In Rust they live in the same file, in a #[cfg(test)] mod tests block at the bottom, and cargo test runs them. Doing this now gives you a self-verification mechanism for every later step.

expected 
44.3 / 42.0   ->  55 AA 01 01 06 04 04 03 04 02 00 18
blank / blank ->  55 AA 01 01 06 EE EE EE EE EE EE 9B

Add clamping cases: 0.0 gives [0,0,0], 99.9 gives [9,9,9], 150.0 clamps to [9,9,9], -5.0 to [0,0,0]. Then a self-consistency test that byte 11 equals the low byte of the sum of bytes 0–10.

Run the tests in both profiles — cargo test and cargo test --release. If they disagree, you have the u8 overflow bug, and this is the cheapest possible way to find it.

Reference implementation — step 1
src/main.rs 
const BLANK: [u8; 3] = [0xEE, 0xEE, 0xEE];

/// A temperature that may not be available. `None` blanks half the panel.
type Reading = Option<f32>;

fn digits(r: Reading) -> [u8; 3] {
    match r {
        None => BLANK,
        Some(c) => {
            // Clamp before casting: a 3-digit temperature has nowhere to go,
            // and `as` saturates for floats but wraps for integers.
            let tenths = (c.clamp(0.0, 99.9) * 10.0).round() as u32;
            [
                (tenths / 100) as u8,
                (tenths / 10 % 10) as u8,
                (tenths % 10) as u8,
            ]
        }
    }
}

fn build_packet(cpu: Reading, gpu: Reading) -> [u8; 12] {
    let mut p = [0u8; 12];
    p[0..2].copy_from_slice(&[0x55, 0xAA]);
    p[2..5].copy_from_slice(&[0x01, 0x01, 0x06]);
    p[5..8].copy_from_slice(&digits(cpu));
    p[8..11].copy_from_slice(&digits(gpu));

    // Sum in u32: eleven bytes overflow a u8, which panics in debug builds.
    let sum: u32 = p[..11].iter().map(|&b| b as u32).sum();
    p[11] = sum as u8;
    p
}
src/main.rs — bottom of the file 
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn known_vectors() {
        assert_eq!(
            build_packet(Some(44.3), Some(42.0)),
            [0x55, 0xAA, 0x01, 0x01, 0x06, 4, 4, 3, 4, 2, 0, 0x18]
        );
        assert_eq!(
            build_packet(None, None),
            [0x55, 0xAA, 0x01, 0x01, 0x06, 0xEE, 0xEE, 0xEE, 0xEE, 0xEE, 0xEE, 0x9B]
        );
    }

    #[test]
    fn clamps_out_of_range() {
        assert_eq!(digits(Some(0.0)), [0, 0, 0]);
        assert_eq!(digits(Some(99.9)), [9, 9, 9]);
        assert_eq!(digits(Some(150.0)), [9, 9, 9]);
        assert_eq!(digits(Some(-5.0)), [0, 0, 0]);
    }

    #[test]
    fn checksum_matches_body() {
        let p = build_packet(Some(44.3), Some(42.0));
        let sum: u32 = p[..11].iter().map(|&b| b as u32).sum();
        assert_eq!(sum as u8, p[11]);
    }
}

2Read one temperature

Get 47.1 out of /sys/class/hwmon/hwmon4/temp1_input. Hardcode the path — you will break it deliberately in step 3.

Read the file, trim it, parse it, divide by a thousand. Four operations, and two of them can fail — which makes this the step where you meet Result and the ? operator, the single most important thing to get comfortable with in Rust.

? means “if this failed, return the error from this function immediately; otherwise give me the value”. It is if err != nil { return err } as a single character. For it to work, your function has to return a Result, and fn main() is allowed to do that too.

Reach for

std::fs::read_to_string, .trim(), .parse(). For the error type, use Box<dyn Error>: it accepts any error, including a plain String, which is what lets you attach the file path.

Why Box<dyn Error>

This one function produces two different error types — an io::Error from reading and a ParseIntError from parsing — and ? will not unify them on its own. Box<dyn Error> is a box that holds any of them.

Treat it as provisional and do not go building a custom error enum with From implementations. That is the fastest known route to deciding Rust error handling is miserable, and you do not need it — this type carries the whole program.

Gotcha · the trailing newline

The file really contains 47125\n. Skip .trim() and .parse() fails with invalid digit found in string, which never mentions whitespace and reads like the file is corrupt. Trim on read, as a reflex.

Gotcha · you cannot return what .trim() gives you

This is your first real encounter with ownership, and it is worth slowing down for.

read_to_string hands you a String that owns a heap buffer. .trim() hands back a &str — a view into that buffer, not a copy. When the function returns, the String is dropped and the buffer freed, so the view would point at nothing. Rust refuses: cannot return value referencing local variable.

The fix is .trim().to_string(), which allocates a fresh owned string. Coming from Go, where slicing a string is free, that feels wasteful. It is one small allocation per second — irrelevant here, and it buys you a function whose return value has no strings attached. Returning owned values everywhere is the reason you will never write a lifetime annotation in this project.

Gotcha · integer division eats the decimal

47125 / 1000 is 47. You need milli as f32 / 1000.0. Worth noticing that you could avoid floats entirely — (milli + 50) / 100 gives 471 tenths directly, which is exactly what the digit splitter wants, with no rounding subtleties. Either is fine; the point is that Rust makes you choose, so choose on purpose.

Checkpoint

cat /sys/class/hwmon/hwmon4/temp1_input prints something like 47125; your program prints 47.1. Cross-check with sensors.

Then break it twice on purpose: point it at a path that does not exist, and at .../name, which exists but will not parse. Both should print one clean line naming the file. This proves your error plumbing before anything complicated rides on it.

One oddity you will notice: an error returned from main prints as Error: Os { code: 2, kind: NotFound, … } rather than a sentence, because main formats it with Debug. That is expected, not a mistake on your part.

Reference implementation — step 2
src/main.rs 
use std::error::Error;
use std::fs;
use std::path::Path;

/// Reads a small sysfs file and trims the trailing newline. Every sysfs read
/// goes through here so the trim cannot be forgotten.
fn read_sysfs(path: &Path) -> Result<String, Box<dyn Error>> {
    let raw = fs::read_to_string(path).map_err(|e| format!("read {}: {e}", path.display()))?;
    // to_string() because `raw` dies at the end of this function and a
    // &str into it would dangle.
    Ok(raw.trim().to_string())
}

/// Degrees Celsius from a hwmon tempN_input file, which holds millidegrees.
fn read_temp(path: &Path) -> Result<f32, Box<dyn Error>> {
    let text = read_sysfs(path)?;
    let milli: i32 = text
        .parse()
        .map_err(|e| format!("parse {}: {e}", path.display()))?;
    Ok(milli as f32 / 1000.0)
}

3Find the sensors

Replace the hardcoded path with a scan: given a driver name like k10temp, find its tempN_input files and their labels.

Earn the step first. Reboot, or run sudo udevadm trigger, and check whether hwmon4 is still k10temp. The numbering is assigned in driver-probe order and moves between boots.

The shape: read /sys/class/hwmon, and for each entry read its name file and keep the ones matching the driver you want. Then in each of those directories, find the files called temp*_input and read the matching _label beside each.

Reach for

fs::read_dir, PathBuf, Path::join, Vec. str::starts_with and ends_with for matching filenames. .ok() to turn a Result you do not care about into an Option. A plain struct to pair a path with its label — with #[derive(Debug)] on it so you can print it with {:?}.

Gotcha · read_dir gives you two layers of Result

fs::read_dir(path) returns a Result — opening a directory can fail — and iterating it yields another Result per entry, because reading can fail partway through. So you handle failure twice.

Two idioms: let entry = entry?; inside the loop propagates each error, or .flatten() on the iterator silently drops failed entries. Flatten swallows errors, which sounds bad and is actually right here — an unreadable entry in /sys/class/hwmon is one you did not want.

Gotcha · never filter on is_dir()

The highest-severity silent failure in this project, and the compiler is perfectly happy with it.

Every entry under /sys/class/hwmon and /sys/class/hidraw is a symlink into /sys/devices/…. DirEntry::file_type() reports the type of the link, so .is_dir() is false for every single one. Filter on it and you get an empty result set, no error, no panic — just nothing.

Either use entry.path().is_dir(), which follows the link, or simply try to read the name file and skip entries where that fails. The second is what the reference does, and it is more robust anyway.

Gotcha · PathBuf, Path, OsString, Cow

Where Go has one string, Rust has a small family. The rules of thumb:

  • PathBuf is to &Path what String is to &str — owned versus borrowed.
  • Build paths with .join(), never format!("{}/{}").
  • Print them with .display(); a path is not directly printable because it is not guaranteed to be UTF-8.
  • entry.file_name() gives an OsString. To compare it as text you want .to_string_lossy(), which returns a Cow<str> — a type that means “borrowed unless I had to allocate”. It shows up in error messages and looks alien; you can treat it as a string.

The task that forces all of this is deriving temp1_label from temp1_input. Do it by trimming the suffix off the filename and rejoining, not by .to_str().unwrap().replace(…) — that panics on non-UTF-8 and is fragile.

Gotcha · numbering has holes, and iteration is unordered

k10temp here exposes temp1, temp3 and temp4 — there is no temp2. Any for i in 1..=n loop is wrong. Enumerate, never count.

read_dir also returns entries in no particular order, so sort if you care. And if you do sort, remember that hwmon10 sorts before hwmon2 lexically.

Gotcha · labels are optional, and that is Option, not Result

spd5118 and ath12k_hwmon have no _label files at all. A missing label is normal. Model it as Option<String> and produce it with read_sysfs(&p).ok() — do not let a RAM sensor you do not care about abort your whole scan.

Checkpoint

Print what you found with {:?} and diff against the shell:

shell 
for d in /sys/class/hwmon/hwmon*; do echo "$d $(cat $d/name)"; done

Two specific things. Did you find k10temp's temp3 and temp4 despite there being no temp2? And did you get any results — an empty list means the symlink trap.

Reference implementation — step 3
src/main.rs 
use std::path::PathBuf;

#[derive(Debug)]
struct Sensor {
    path: PathBuf,
    label: Option<String>, // many drivers expose no label at all
}

/// Every hwmon directory belonging to one driver. Note this does not filter
/// on is_dir(): entries under /sys/class/hwmon are symlinks, so file_type()
/// reports false for all of them. Reading `name` is the real test.
fn hwmon_by_driver(driver: &str) -> Vec<PathBuf> {
    let mut out = Vec::new();
    let Ok(entries) = fs::read_dir("/sys/class/hwmon") else {
        return out;
    };
    for entry in entries.flatten() {
        let dir = entry.path();
        if read_sysfs(&dir.join("name")).is_ok_and(|n| n == driver) {
            out.push(dir);
        }
    }
    out.sort();
    out
}

/// Every temperature sensor in one hwmon directory. Enumerates rather than
/// counting: k10temp exposes temp1, temp3 and temp4 with no temp2.
fn temp_inputs(dir: &Path) -> Vec<Sensor> {
    let mut out = Vec::new();
    let Ok(entries) = fs::read_dir(dir) else {
        return out;
    };
    for entry in entries.flatten() {
        let file_name = entry.file_name();
        let name = file_name.to_string_lossy();
        if !(name.starts_with("temp") && name.ends_with("_input")) {
            continue;
        }
        let label_path = dir.join(format!("{}_label", name.trim_end_matches("_input")));
        out.push(Sensor {
            path: entry.path(),
            label: read_sysfs(&label_path).ok(), // absent is normal
        });
    }
    out.sort_by(|a, b| a.path.cmp(&b.path));
    out
}

4Pick the right GPU

Given two amdgpu instances, choose the discrete card and not the integrated one — and meet iterators properly while doing it.

A Ryzen desktop chip with integrated graphics gives you two amdgpu hwmon directories. One is your RX 9070; the other is an iGPU sitting at idle forever.

PathInputsLabelsWhich
hwmon23edge, junction, memDiscrete
hwmon31edgeiGPU

The heuristic: a discrete card reports edge, junction and memory; an integrated one reports only edge. Among candidate directories for a driver, take the one with the most temperature inputs, then within it prefer a specific label.

This is the one place in the project where an iterator chain is clearly better than a loop, which makes it a good place to actually learn them rather than being told to. .map() transforms each item, .max_by_key() picks a winner, and the ? at the end unwraps the Option it returns or bails out early.

Gotcha · iterators hand back references

.max_by_key() on a borrowed iterator gives you Option<&T> — a reference — and then you want an owned value to return. This is the “everything is a reference and I need a value” loop that makes iterator chains frustrating at first.

Two escapes: .clone() the thing you need (a PathBuf clone is one small allocation, and it is fine), or use .into_iter() instead of .iter() so the iterator yields owned values in the first place. The reference does the second, then clones one path at the end.

It's a heuristic, so say what you picked

This guess is right on every machine anyone has tested and could be wrong on yours. One eprintln! at startup naming the chosen paths turns a baffling wrong number into a one-second diagnosis.

Checkpoint

Your finder should land on hwmon4/temp1_input (Tctl) for the CPU and hwmon2/temp1_input (edge) for the GPU — not hwmon3. Load the GPU with something and watch the number move.

Run cargo clippy here in particular. Iterator code is where it has the most to teach, and its suggestions on this step are usually worth taking.

Reference implementation — step 4
src/main.rs 
/// Picks a temperature input for a driver, preferring the first label in
/// `preferred` that exists. Among several instances of the same driver
/// (a discrete GPU and an iGPU both bind amdgpu) the one exposing the most
/// sensors wins: a discrete card reports edge+junction+mem, an iGPU only edge.
fn find_sensor(driver: &str, preferred: &[&str]) -> Option<PathBuf> {
    let best = hwmon_by_driver(driver)
        .into_iter()
        .map(|dir| temp_inputs(&dir))
        .max_by_key(|inputs| inputs.len())?;

    if best.is_empty() {
        return None;
    }
    for want in preferred {
        for s in &best {
            if s.label.as_deref().is_some_and(|l| l.eq_ignore_ascii_case(want)) {
                return Some(s.path.clone());
            }
        }
    }
    Some(best[0].path.clone())
}

fn find_cpu() -> Option<PathBuf> {
    find_sensor("k10temp", &["Tctl"]).or_else(|| find_sensor("coretemp", &["Package id 0"]))
}

fn find_gpu() -> Option<PathBuf> {
    find_sensor("amdgpu", &["edge"]).or_else(|| find_sensor("nvidia", &[]))
}

5Find the device and write to it

Locate your /dev/hidrawN by USB ID, then put a number on the panel from your own code.

Discovery is the same directory-scanning shape as step 3 with a different matcher: walk /sys/class/hidraw/*, read each device/uevent, and look for the HID_ID line. You already know how to do this — write it before opening the solution.

Gotcha · eight hex digits, not four

HID_ID=0003:00002022:00000522. The vendor and product fields are zero-padded to eight digits. Searching for "2022:0522" matches nothing, silently. Build the needle with format!(":{VENDOR_ID:08X}:{PRODUCT_ID:08X}") and compare case-insensitively, since the kernel writes lowercase.

This exact bug shipped in the first draft of the Python version in this repo.

The write half is where the foundations page's two rules bite. Your buffer is thirteen bytes — a leading 0x00 report ID, then the packet — and it goes out in one call.

Gotcha · the trait must be imported to be callable

You will write file.write_all(&buf) and get no method named write_all found for struct File, which is baffling because File obviously can be written to.

write_all comes from the Write trait, and in Rust a trait's methods only exist on a type when the trait is in scope. Add use std::io::Write; at the top. This is the concrete difference from Go's implicit interface satisfaction, and it catches every Go programmer exactly once.

Gotcha · the file has to be mut

write_all takes &mut self, so let file = File::open(…) followed by file.write_all(…) gives you cannot borrow as mutable.

mut here describes the binding, not the file on disk — you are not declaring the file mutable, you are declaring that you will call methods that need exclusive access. Say let mut file = ….

The surprising escape hatch, once you meet it: (&file).write_all(…) also compiles, because the standard library implements Write for &File as well.

Reach for

OpenOptions::new().write(true).open(path). Not File::create, which adds O_CREAT|O_TRUNC — harmless on a character device but wrong, and it will fail confusingly under the hardened systemd unit in step 9. Do not add .read(true) “to be safe”: you never read from this device, and the IN endpoint would block if you tried.

Reaching for the wrong tool

BufWriter. It is the reflex from Go's bufio.Writer and it silently breaks the protocol here: hidraw maps one write() syscall to one HID report, so buffering can split your report or hold it until a flush you forgot. File::write_all is already one syscall for a buffer this size.

And, one more time, because search results will push you there: not hidapi, not rusb. They require detaching the kernel driver, drag in a C toolchain, and buy you nothing over a file you can already open.

Checkpoint

Aim at a scratch file before the real device — no root needed:

shell 
$ hexdump -C /tmp/panel.bin
00000000  00 55 aa 01 01 06 04 04  03 04 02 00 18
$ wc -c /tmp/panel.bin
13 /tmp/panel.bin

Exactly 13 bytes. Then the definitive test against the real node:

shell 
$ strace -e trace=write ./target/debug/antec-display
write(3, "\0U\252\1\1\6\4\4\3\4\2\0\30", 13) = 13

One write of 13 bytes per packet. If you get Permission denied, that is the udev rule, not your code — see the foundations page.

Reference implementation — step 5
src/main.rs 
use std::fs::{File, OpenOptions};
use std::io::Write; // without this, .write_all() does not exist on File

const VENDOR_ID: u16 = 0x2022;
const PRODUCT_ID: u16 = 0x0522;

/// Finds the panel by USB ID rather than device number, because
/// /dev/hidrawN is assigned in enumeration order and moves.
fn find_hidraw() -> Option<PathBuf> {
    // HID_ID=0003:00002022:00000522 — eight hex digits per field, not four.
    let needle = format!(":{VENDOR_ID:08X}:{PRODUCT_ID:08X}");

    let mut nodes: Vec<PathBuf> = Vec::new();
    for entry in fs::read_dir("/sys/class/hidraw").ok()?.flatten() {
        let Ok(text) = fs::read_to_string(entry.path().join("device/uevent")) else {
            continue;
        };
        if text.to_uppercase().contains(&needle) {
            nodes.push(Path::new("/dev").join(entry.file_name()));
        }
    }
    nodes.sort();
    nodes.into_iter().next()
}

/// Writes one HID output report. The leading zero is the report-ID byte,
/// which the kernel strips because this descriptor declares no report IDs.
/// One buffer, one write_all: hidraw maps each write() syscall to one report.
fn send(file: &mut File, packet: &[u8; 12]) -> std::io::Result<()> {
    let mut buf = [0u8; 13];
    buf[1..].copy_from_slice(packet);
    file.write_all(&buf)
}

6The loop

Read both sensors, build, send, wait a second, repeat.

Mechanically this is loop { … } and thread::sleep(Duration::from_secs(1)). That is the whole thing.

Before you go looking for something fancier

One thread, one blocking sleep, no channels, no ticker abstraction, no tokio. For a task that happens once a second this is not a compromise — it is the correct and complete design, and anything else is strictly more code doing strictly more work. Rust makes async so visible that beginners assume they are supposed to reach for it. Not here.

Error policy in a daemon

Inside the loop, errors are not propagated with ?. A sensor read that fails becomes a blank half of the panel and a line on stderr. If you let errors escape the loop, the process exits, systemd restarts it, and you get a restart loop instead of a recovery — worse than the original problem and harder to diagnose.

This is also where .unwrap() stops being acceptable. It is fine while exploring; in a daemon a single transient error panics the process. Prefer .expect("some message") over bare .unwrap() even in throwaway code, so the panic tells you which one blew up.

Reach for

Option::as_deref() to turn your Option<PathBuf> into an Option<&Path> without giving up ownership. And note that ? works on Option too, not just Result — which makes “no path, so no reading” a single character.

Checkpoint

Watch the panel for ten seconds; the numbers move. Cross-check against watch -n1 sensors. Check top — CPU should be indistinguishable from zero. If it is pegged, your sleep is missing or outside the loop.

Reference implementation — step 6
src/main.rs 
use std::thread;
use std::time::Duration;

/// Reads a sensor, turning any failure into a blanked half-panel.
/// The `?` on an Option returns None early when there is no path at all.
fn read_or_blank(path: Option<&Path>) -> Reading {
    let path = path?;
    match read_temp(path) {
        Ok(c) => Some(c),
        Err(e) => {
            eprintln!("sensor: {e}");
            None
        }
    }
}

fn describe(p: &Option<PathBuf>) -> String {
    match p {
        Some(p) => p.display().to_string(),
        None => "none".to_string(),
    }
}

fn main() -> Result<(), Box<dyn Error>> {
    let cpu = find_cpu();
    let gpu = find_gpu();
    eprintln!("cpu sensor: {}", describe(&cpu));
    eprintln!("gpu sensor: {}", describe(&gpu));
    if cpu.is_none() && gpu.is_none() {
        return Err("no CPU or GPU sensor found under /sys/class/hwmon".into());
    }

    let path = find_hidraw().ok_or("no device 2022:0522 found")?;
    let mut file = OpenOptions::new().write(true).open(&path)?;
    eprintln!("opened {}", path.display());

    loop {
        let packet = build_packet(
            read_or_blank(cpu.as_deref()),
            read_or_blank(gpu.as_deref()),
        );
        if let Err(e) = send(&mut file, &packet) {
            eprintln!("write: {e}"); // step 7 makes this recover
        }
        thread::sleep(Duration::from_secs(1));
    }
}

7Survive a replug

When the device goes away and comes back, reopen it instead of dying or writing forever to a dead descriptor.

The program now needs to remember something between iterations — whether the device is open — which is what a struct with an impl block is for. Hold an Option<File>: None means “not open”, and dropping the File back to None is how you close it.

You never call close()

Rust closes the file when the File value is dropped — when it goes out of scope, or when you overwrite it with None. There is no defer f.Close() because there is nothing to defer. This is RAII, and it is one of the genuinely nicer things about the language.

Learn it now, and also learn its one limit, which you will meet in step 8: drop does not run when a process is killed by a signal.

Gotcha · two &mut self borrows at once

The natural way to write send does not compile:

does not compile 
let file = self.ensure_open()?;        // borrows self mutably
if let Err(e) = file.write_all(&buf) {
    self.file = None;                 // second mutable borrow — E0499
    return Err(Box::new(e));
}

The first borrow is still alive when you try to touch self again. The fix is to end the borrow before you need self back: do the write, store the result in a local, and only then modify self. The reference does exactly that, and it is worth writing the broken version once so you recognise E0499 later.

Gotcha · re-run discovery, don't reuse the path

After a replug the device may come back as a different /dev/hidrawN. Reopening the remembered path can get you a working handle on somebody else's keyboard. Discovery is cheap; run it again.

Checkpoint

Make the device go away — physically unplug the internal header, or do it in software:

shell 
# the USB path comes from HID_PHYS in the uevent file — here, 1-7
echo 0 | sudo tee /sys/bus/usb/devices/1-7/authorized
sleep 2
echo 1 | sudo tee /sys/bus/usb/devices/1-7/authorized

The program should log the failure, reopen a couple of seconds later, and never exit. If it panics, you still have an .unwrap() in the loop body.

Reference implementation — step 7
src/main.rs 
/// Owns the open device, reopening it after an unplug.
struct Display {
    file: Option<File>,
}

impl Display {
    fn new() -> Self {
        Display { file: None }
    }

    fn ensure_open(&mut self) -> Result<(), Box<dyn Error>> {
        if self.file.is_some() {
            return Ok(());
        }
        // Re-discover rather than reusing a remembered path: the node number
        // can change across a replug.
        let path = find_hidraw().ok_or("no device 2022:0522 found")?;
        let file = OpenOptions::new()
            .write(true)
            .open(&path)
            .map_err(|e| format!("open {}: {e}", path.display()))?;
        eprintln!("opened {}", path.display());
        self.file = Some(file);
        Ok(())
    }

    fn send(&mut self, packet: &[u8; 12]) -> Result<(), Box<dyn Error>> {
        self.ensure_open()?;
        let mut buf = [0u8; 13];
        buf[1..].copy_from_slice(packet);

        // Store the result first so the borrow of self.file ends here.
        // Writing `if let Err(e) = self.file.as_mut()...` and then assigning
        // to self.file inside the block is E0499.
        let result = self.file.as_mut().unwrap().write_all(&buf);
        if let Err(e) = result {
            self.file = None; // dropping the File closes the fd
            return Err(Box::new(e));
        }
        Ok(())
    }
}

8Graceful shutdown

On SIGINT or SIGTERM, blank the panel and exit cleanly instead of leaving a stale number frozen on your case.

First, see the problem. Run the service, then stop it, and watch the panel keep whatever number was there at the moment the process died. Nothing refreshes that display but you.

The one place Rust is worse than Go

Rust's standard library has no signal handling. None, at any level. There is no equivalent of Go's os/signal. Ctrl-C takes the default SIGINT disposition and your process dies instantly.

And the RAII you learned in step 7 does not save you: Drop does not run when a process is killed by a signal. Cleanup code in a destructor is simply skipped. This is worth internalising — it is a real limit on a pattern that otherwise feels bulletproof.

You have three genuine options, and it is worth understanding that adding a crate is not automatically the answer:

OptionCostVerdict
signal-hookOne dependency (plus libc), safe APIRecommended. Handles both signals, works in the foreground and under systemd
ctrlcOne dependency; needs its termination feature enabled for SIGTERMSimpler API, easy to configure wrongly and then only catch Ctrl-C
systemd ExecStopPost=Zero dependenciesHave systemd run your binary again with a --blank flag after the service stops. Arguably the most Unix-native answer, and it does nothing for Ctrl-C in a terminal
Reach for

cargo add signal-hook — your first external dependency, at step 8, which is itself worth noticing. Then signal_hook::flag::register(SIGTERM, Arc::clone(&stop)), where stop is an Arc<AtomicBool>.

Treat that type as documented boilerplate rather than a concurrency lecture. The reasoning in one sentence: the signal handler runs outside your normal control flow, so the flag has to be shared (Arc) and safe to touch from two places at once (AtomicBool). Ordering::Relaxed is sufficient for a single flag.

Gotcha · a one-second sleep is a one-second shutdown

If your loop sleeps for a full second, a Ctrl-C lands mid-sleep and nothing happens until it finishes. Under systemd that is a sluggish stop; in a terminal it feels broken.

Sleep in short slices and check the flag between them — ten 100 ms sleeps instead of one 1 s sleep. It is three extra lines and the shutdown becomes instant.

Checkpoint

Foreground, Ctrl-C: the panel shows --.- within about a second and the process exits 0 — check with echo $?. Then kill -TERM the PID and confirm identical behaviour.

Now the instructive one: kill -KILL it. The panel keeps its stale reading, because SIGKILL cannot be caught by anything and no destructor runs. That is not a bug in your program — it is the step-7 RAII lesson meeting its limit, and it is worth seeing once.

Reference implementation — step 8
Cargo.toml 
[dependencies]
signal-hook = "0.4"
src/main.rs — main, revised 
use std::sync::atomic::{AtomicBool, Ordering};
use std::sync::Arc;

fn main() -> Result<(), Box<dyn Error>> {
    let cpu = find_cpu();
    let gpu = find_gpu();
    eprintln!("cpu sensor: {}", describe(&cpu));
    eprintln!("gpu sensor: {}", describe(&gpu));
    if cpu.is_none() && gpu.is_none() {
        return Err("no CPU or GPU sensor found under /sys/class/hwmon".into());
    }

    // The handler runs outside normal control flow, so the flag must be
    // shared (Arc) and safe to touch concurrently (AtomicBool).
    let stop = Arc::new(AtomicBool::new(false));
    signal_hook::flag::register(signal_hook::consts::SIGTERM, Arc::clone(&stop))?;
    signal_hook::flag::register(signal_hook::consts::SIGINT, Arc::clone(&stop))?;

    let mut display = Display::new();

    while !stop.load(Ordering::Relaxed) {
        let packet = build_packet(
            read_or_blank(cpu.as_deref()),
            read_or_blank(gpu.as_deref()),
        );
        if let Err(e) = display.send(&packet) {
            eprintln!("display: {e}");
        }
        // Sleep in slices so shutdown doesn't wait out a full second.
        for _ in 0..10 {
            if stop.load(Ordering::Relaxed) {
                break;
            }
            thread::sleep(Duration::from_millis(100));
        }
    }

    eprintln!("shutting down, blanking panel");
    let _ = display.send(&build_packet(None, None)); // best effort
    Ok(())
}

9Ship it

A release binary, a udev rule, a systemd unit, and a panel that comes back by itself after a reboot.

shell 
cargo build --release
ls -l target/release/antec-display
ldd target/release/antec-display    # libc and friends, no interpreter

Release builds are where the overflow-check difference from step 1 lives, so run cargo test --release too — you want both profiles green before this becomes a service that starts at boot.

The repo already has a udev rule and a systemd unit written for the Python daemon. Reuse both; only ExecStart changes. The unit's hardening is worth reading rather than copying blind — ProtectSystem=strict makes the filesystem read-only except /dev, /proc and /sys, which is exactly this program's access and nothing more.

shell 
sudo install -m0755 target/release/antec-display /usr/local/bin/antec-display
sudo cp 99-antec-display.rules /etc/udev/rules.d/
sudo cp antec-display.service /etc/systemd/system/
sudo sed -i 's|^ExecStart=.*|ExecStart=/usr/local/bin/antec-display|' \
  /etc/systemd/system/antec-display.service
sudo udevadm control --reload-rules && sudo udevadm trigger --subsystem-match=hidraw
sudo systemctl daemon-reload
sudo systemctl enable --now antec-display
You do not need a logging crate

Under systemd, anything on stdout or stderr is captured by journald with timestamps and metadata. eprintln! is genuinely sufficient — no log, no env_logger, no tracing. Demonstrate it to yourself with journalctl -u and the temptation goes away.

The same restraint applies to clap for a couple of flags and serde for config you do not have. Your dependency count for this whole project is one.

Optional, if you want the practice

std::env::args() for a few flags — --once, --dry-run to print hex instead of writing, --device to override discovery — and std::env::var for ANTEC_CPU_SENSOR-style overrides, which returns a Result you can .ok() into an Option. Deliberately not clap.

If error messages start annoying you, that is the moment anyhow earns its place: .context(…) attaches the file path to an error without you writing map_err(|e| format!(…)) every time. Add it when you feel the pain, not before.

Checkpoint

systemctl status antec-display is clean, and journalctl -u antec-display -f shows your two startup lines naming the chosen sensors — which also proves eprintln! reaches the journal with no logging crate.

Restart twice. systemctl stop and confirm the panel blanks rather than freezing, which is step 8 working through systemd's SIGTERM.

Then reboot. If it finds the right hidraw node and the right hwmon directories on a machine where the numbering has shifted, steps 3 through 5 earned their keep — and you have written a real Rust program that runs on your machine whether or not you are looking at it.
