01What the panel actually is

Not a driver project. Not a USB project, really. A file-writing project.

The temperature readout on the top I/O of the Performance 1 FT is a small display module wired to an internal USB 2.0 header on your motherboard. It enumerates as an ordinary USB HID device, and the kernel binds its generic HID driver to it automatically at boot. Nothing needs installing for it to appear:

lsusb 
Bus 001 Device 002: ID 2022:0522 DINK_HID_DEVICE DINK_HID_DEVICE

“DINK” is the display controller vendor, not Antec — the same module shows up in the Antec Flux Pro and a few other cases, which is why the protocol was already public before either of us looked at it. The full descriptor is worth a glance:

lsusb -v -d 2022:0522 (abridged) 
bcdUSB               1.01
bDeviceClass            0
iSerial                 3 2015-03-21
  Interface Descriptor:
    bInterfaceClass       3 Human Interface Device
    bInterfaceSubClass    0
    bNumEndpoints         2
  Endpoint Descriptor:
    bEndpointAddress   0x81  EP 1 IN     Interrupt   64 bytes
  Endpoint Descriptor:
    bEndpointAddress   0x02  EP 2 OUT    Interrupt   64 bytes

Two interrupt endpoints, 64 bytes each. You will only ever use the OUT one. There is no configuration to negotiate, no handshake, no initialisation sequence — the device is ready the moment it enumerates, and it forgets everything the moment you stop writing to it.

Nothing here is fragile

The worst outcome of a malformed packet is a garbled or frozen readout, fixed by sending a correct packet or replugging the header. There is no writable firmware, no EEPROM, and no bootloader on this device. Experiment freely.

02Why hidraw, and not libusb

Search for “USB HID from Go” or “USB HID from Rust” and every result points at a libusb binding — gousb, rusb, hidapi, pyusb. Several of the existing Antec projects on GitHub are built that way. It works, and it is the wrong path here.

Because the kernel has already claimed this device with hid-generic, libusb cannot simply talk to it. You must first detach the kernel driver from the interface. That costs you three things: a C toolchain and libusb/libudev headers at build time, root at runtime, and — the one that actually matters — the physical toggle button on your case's top I/O, which stops working while the interface is detached.

Meanwhile the kernel is already exposing the device as a character device you can open and write to like any other file:

shell 
$ ls -l /dev/hidraw0
crw------- 1 root root 243, 0 Aug  6 21:42 /dev/hidraw0
The rule

If the kernel already gives you a file, use the file. Every language on earth can open a file and write bytes to it, which is exactly why this project has a zero-dependency solution in both Go and Rust.

03Reading the report descriptor

Two facts about the write path get asserted constantly and explained rarely: the report is 64 bytes, and you must prefix your write with a zero byte. Both come straight out of the device's HID report descriptor, which you can read without any tooling:

shell 
$ sudo hexdump -C /sys/class/hidraw/hidraw0/device/report_descriptor
00000000  06 a0 ff 09 01 a1 01 09  02 a1 00 06 a1 ff 09 03
00000010  09 04 15 80 25 7f 35 00  45 ff 75 08 95 40 81 02
00000020  09 05 09 06 15 80 25 7f  35 00 45 ff 75 08 95 40
00000030  81 02 09 05 09 06 15 80  25 7f 35 00 45 ff 75 08
00000040  95 40 91 02 c0 c0

Seventy bytes. HID descriptors are a flat stream of items, each a one-byte tag followed by its data. Decoded, with the parts that matter to us highlighted:

BytesItemMeaning
06 A0 FFUsage PageVendor-defined 0xFFA0 — no standard semantics, so no kernel driver will try to interpret our reports as a keyboard or mouse
09 01 / A1 01Usage, CollectionApplication collection opens
09 02 / A1 00Usage, CollectionPhysical collection opens
75 08Report Size8 bits per field
95 40Report Count64 fields — so 64 × 8 bits = 64 bytes per report
81 02InputAn IN report, device → host. Appears twice. You never read these.
91 02OutputAn OUT report, host → device. This is the one you write. 64 bytes, from the Report Size and Report Count above it.
C0 C0End Collection ×2Done
Where the zero byte comes from

Notice what is not in those 70 bytes: any 0x85 item, which is the tag for Report ID. This device declares no report IDs at all.

The hidraw write interface always treats the first byte of your buffer as a report ID. When a device has none, the kernel requires that byte to be 0x00 and strips it before the report goes on the wire. So a 12-byte packet becomes a 13-byte write(), and the leading zero never reaches the display.

Twelve bytes, sent about once a second. That is the entire protocol.

Digits are values, not characters

44.3 °C encodes as 0x04 0x04 0x03. Not '4' '4' '3', which would be 0x34 0x34 0x33. The display wants the numeric value of each digit and drives its segments from that directly. This trips people up because every other text-ish protocol they have met works the other way.

Blanking

Sending 0xEE 0xEE 0xEE in place of a digit triple blanks that half of the panel to --.-. Useful in three situations: a sensor you could not find, a reading that failed this tick, and shutdown — so the panel does not freeze forever on whatever number happened to be there when your process died.

Two test vectors

Keep these. They are the anchor for every checkpoint in both tutorials, and you can verify both by hand in about a minute.

known-good packets 
44.3 °C / 42.0 °C   ->  55 AA 01 01 06  04 04 03  04 02 00  18
blank   / blank     ->  55 AA 01 01 06  EE EE EE  EE EE EE  9B
Gotcha · the checksum overflows immediately

0x55 + 0xAA + 0x01 = 0x100. The accumulator exceeds a single byte on the third byte of every packet, before any temperature data is involved.

This has opposite consequences in the two languages, and both tutorials return to it: Go wraps silently and quietly gives you the right answer; Rust panics in a debug build and wraps correctly in a release build, which presents as “my program only crashes when I'm developing”. Accumulate in a wider integer type and narrow once at the end.

What is not in the protocol

The packet always carries both temperatures. The button on your top I/O chooses which one the panel shows, and it does that entirely inside the display module — your program never sees the button press and cannot read or set its state. There is also no brightness control, no colour, no text mode, and no acknowledgement of any kind. iUnity's richer layouts use a second, undocumented protocol that nobody has reverse engineered.

05Two rules for writing

Everything else in both tutorials is ordinary programming. These two rules are the only places where being casual will produce a bug you cannot reason about from the symptom.

Rule one — prefix the report ID byte

Your buffer is 13 bytes: a 0x00, then the 12-byte packet. Section 03 explains why. Get this wrong and the display receives 55 AA 01 01 06 … shifted by one position, fails its own header check, and shows nothing at all — no error, no clue.

Rule two — one buffer, one write() syscall

hidraw maps each write() syscall onto exactly one HID report. Two syscalls are two reports, both malformed. This makes buffered writers actively harmful here, which is counterintuitive: wrapping a file in a buffer is normally free performance.

Reaching for the wrong tool

bufio.Writer in Go, BufWriter in Rust, fmt.Fprintf or write!() called once per field — all of these can split your report across syscalls or hold it until an explicit flush. Build the whole 13-byte buffer in memory, then hand it to a single write_all/Write call.

How to prove you got it right

strace -e trace=write ./your-program should show exactly one write(3, ..., 13) = 13 per second. Seeing the syscall directly is far more convincing than seeing the right number on the panel, because a torn report can still occasionally look correct.

06Warm-up: light up the panel with no code at all

Do this before you write a line of Go or Rust. It takes thirty seconds and it will save you an evening.

You have a test vector and you know the write rules, so you already have everything needed to drive the display from a shell. Paste the 44.3/42.0 packet, with its leading zero:

shell 
printf '\x00\x55\xaa\x01\x01\x06\x04\x04\x03\x04\x02\x00\x18' \
  | sudo dd of=/dev/hidraw0 bs=13 count=1

The panel should read 44.3. (It will keep reading that until something else writes to it — nothing is refreshing it.) Blank it again with the second vector:

shell 
printf '\x00\x55\xaa\x01\x01\x06\xee\xee\xee\xee\xee\xee\x9b' \
  | sudo dd of=/dev/hidraw0 bs=13 count=1
Why bother

From here on, every failure has two possible causes: your program is wrong, or your understanding of the device is wrong. This one command permanently eliminates the second one. If the panel lit up, the device works, the node is right, and your permissions are fine — so any later problem is in your code, and you can stop second-guessing the hardware.

bs=13 count=1 is not decoration. It forces dd to issue a single 13-byte write, which is rule two enforced by the tool.

If it did not light up, resolve that now rather than after you have written 200 lines. Check the node is really yours (section 10) and that you used sudo — /dev/hidraw0 is root-only until you install a udev rule.

07Reading temperatures

Linux exposes every temperature sensor it knows about under /sys/class/hwmon/ as small text files. No library, no daemon, no lm_sensors dependency — just reads. You do not need NVML for an NVIDIA card or ROCm for an AMD one; both drivers publish through hwmon.

shell 
$ for d in /sys/class/hwmon/hwmon*; do echo "$d  $(cat $d/name)"; done
/sys/class/hwmon/hwmon0  nvme
/sys/class/hwmon/hwmon1  nvme
/sys/class/hwmon/hwmon2  amdgpu
/sys/class/hwmon/hwmon3  amdgpu
/sys/class/hwmon/hwmon4  k10temp
/sys/class/hwmon/hwmon5  spd5118
/sys/class/hwmon/hwmon6  r8169_0_900:00
/sys/class/hwmon/hwmon7  spd5118
/sys/class/hwmon/hwmon8  ath12k_hwmon

Inside each directory: a name file holding the driver name, one or more tempN_input files holding millidegrees Celsius as text, and optionally a matching tempN_label naming the sensor.

shell 
$ cat /sys/class/hwmon/hwmon4/name
k10temp
$ cat /sys/class/hwmon/hwmon4/temp1_input
47125
$ cat /sys/class/hwmon/hwmon4/temp1_label
Tctl

So 47125 means 47.1 °C. Four things about these files will bite you, and all four are load-bearing in both tutorials:

Gotcha · everything ends in a newline

The files really contain k10temp\n and 47125\n — verified with od -c. Parsing "47125\n" as an integer fails in both languages, with an error message that says nothing about whitespace. Worse, comparing "k10temp\n" against "k10temp" fails silently: you simply find no sensors, with no error to trace.

Trim on read. Every sysfs read, immediately, before anything else touches the string.

Gotcha · the numbering has holes

k10temp on this machine exposes temp1, temp3 and temp4. There is no temp2. Any loop of the form for i in 1..=count will either miss sensors or try to read files that do not exist. Enumerate the directory; never count.

Gotcha · labels are optional

spd5118, r8169 and ath12k_hwmon have no tempN_label files at all. A missing label is normal, not an error — model it as an optional value, and never let its absence abort a scan.

Gotcha · every entry is a symlink

This is the nastiest one, because it fails silently and the compiler is happy.

/sys/class/hwmon/hwmon4 is a symlink into the real device tree under /sys/devices/…, and so is every entry under /sys/class/hidraw/. Directory-iteration APIs in both Go and Rust report the type of the link, not its target, so a filter like “only descend into directories” matches nothing at all. You get an empty result set, no error, and no hint about why.

One more, which you will only notice after a reboot: hwmon numbering is assigned in driver-probe order and is not stable. Today's hwmon4 is tomorrow's hwmon2. Hardcoding a path is fine while you are getting a first reading on screen; shipping it is a bug that surfaces weeks later. Both tutorials have you hardcode first and then break it deliberately.

08Picking the right sensors

Two halves of the panel, so two sensors. You want to select them by driver name and label rather than by path.

The two-amdgpu problem

A Ryzen desktop chip with integrated graphics plus a discrete card gives you two amdgpu hwmon instances, and picking the wrong one puts your iGPU's idle temperature on the panel forever. On this machine:

PathInputsLabelsWhich
hwmon2temp1, temp2, temp3edge, junction, memDiscrete RX 9070 — what you want
hwmon3temp1edgeGranite Ridge iGPU

The cheap, reliable heuristic: a discrete card reports edge and junction and memory, an integrated one reports only edge. Pick the instance with the most temperature inputs. It is a heuristic rather than a guarantee, so print what you chose at startup — one line in the log turns a mystery into a one-second diagnosis.

Design note · a missing sensor is not an error

If you cannot find a GPU, do not abort. Send 0xEE 0xEE 0xEE for that half and keep going — half a working panel beats a service that refuses to start. The same applies to a read that fails on one tick: blank it, log it, carry on.

09Permissions

/dev/hidraw0 is crw------- root root. Your options, in order of how much you should like them:

A udev rule, so your normal user can write to the node while developing. uaccess hands the device to whoever is logged in at the local seat, which is the same mechanism your webcam and joystick use:

/etc/udev/rules.d/99-antec-display.rules 
KERNEL=="hidraw*", ATTRS{idVendor}=="2022", ATTRS{idProduct}=="0522", \
  TAG+="uaccess", MODE="0660", GROUP="input"
shell 
sudo udevadm control --reload-rules
sudo udevadm trigger --subsystem-match=hidraw
ls -l /dev/hidraw0    # should now show your user via an ACL: crw-rw----+

Run as root under systemd. For the shipped service this is fine and is what the existing Python daemon does — the process reads a handful of sysfs files and writes one device node, and the unit file locks down everything else.

sudo ./your-program while developing. Works, but you will get tired of it, and running a compiler's output as root on every iteration is a habit worth not forming. Install the udev rule.

Gotcha · permission errors look like bugs

The first time you point your program at the real device you are quite likely to get a permission error, and the temptation is to assume your open flags are wrong. They are not. Check ls -l first.

10Debugging toolkit

Six commands cover essentially every problem you will hit. Learn them before you need them.

CommandAnswers
grep -l 0003:00002022:00000522 /sys/class/hidraw/*/device/ueventWhich hidraw node is mine, right now? This is the ground truth your program's discovery code must agree with.
hexdump -C out.binDid I build the bytes I think I built? Write to a scratch file instead of the device and look.
wc -c out.binExactly 13? 0 means an unflushed buffer; 14 means a stray newline.
strace -e trace=write ./progOne write(3, ..., 13) = 13 per tick, or did my report get torn in two?
watch -n1 sensorsIs the number on the panel the number the kernel reports?
journalctl -u antec-display -fWhat did the service say? Plain stdout/stderr lands here with no logging library.

That first one deserves a closer look, because it is the exact string your discovery code will search for and the single most likely thing to silently not match:

shell 
$ cat /sys/class/hidraw/hidraw0/device/uevent
DRIVER=hid-generic
HID_ID=0003:00002022:00000522
HID_NAME=DINK_HID_DEVICE DINK_HID_DEVICE
HID_PHYS=usb-0000:13:00.0-7/input0
HID_UNIQ=2015-03-21
Gotcha · the ID fields are zero-padded to eight digits

HID_ID is bus:vendor:product, and the vendor and product fields are padded to eight hex digits — not four. Searching for "2022:0522" matches nothing. You want ":00002022:00000522".

This exact bug shipped in the first draft of the Python version in this repo. It fails with no error: discovery just quietly finds nothing.

Note that there are fifteen hidraw nodes on this machine, three of them identical Logitech receivers and three identical DOIO keyboards. Scanning for your device by ID is not a theoretical nicety; the numbering genuinely moves.

11What you're building

Both tutorials build the same program in the same order, so you can read one against the other.

The shape is three phases: discover the device and the sensors once at startup, loop forever (read, encode, write, sleep), and shut down cleanly. Deliberately, the tutorials do not build it in that order — they start with the pure encoding logic, which needs no I/O and no hardware, and work outward to the messy edges. That is both easier to learn and the structure you would want in the finished program anyway.

#StepWhy it's here
1The packet builderPure functions, fully testable against the two vectors, no device needed
2Read one temperatureHardcoded path. First file I/O, first error handling
3Find the sensorsDirectory scanning; the symlink and newline traps land here
4Pick the right GPUSmall, verifiable, and the one place iterators are obviously the right tool
5Find the device, write to itFirst light from your own code
6The loopNow it's a program rather than a script
7Survive a replugReopen on error instead of dying; keeps state, so it's where structs earn their place
8Graceful shutdownBlank the panel on the way out. Where Go and Rust diverge hardest
9Ship itRelease build, udev rule, systemd unit, survives a reboot

Decisions worth making once

  • Clamp before you encode. A three-digit temperature has nowhere to go in a three-digit field. Clamp to 0–99.9 °C, and be aware that narrowing casts behave differently for floats and integers in both languages.
  • Keep the file descriptor open. Reopening every second works and is a syscall storm that also hides the unplug case instead of handling it. Open once, reopen only on error.
  • Do not assume the node number survives a replug. On reconnect, re-run discovery rather than reopening the same path.
  • Test against a file, not the device. Point your writer at /tmp/panel.bin and hexdump it. Steps 1 through 5 can be fully verified with no device access and no root.
Optional, and genuinely optional

Some firmware revisions reject a write shorter than the declared 64-byte report. Yours does not appear to, but if the panel stays dark despite a byte-perfect 13-byte write, pad the packet out to 64 bytes with zeros and try again. Treat it as a stretch goal, not a step.
