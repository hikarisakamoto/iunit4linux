01What the panel is

The temperature readout on the top I/O of the Performance 1 FT is a small display module wired to an internal USB 2.0 header on your motherboard. It enumerates as an ordinary USB HID device, and the kernel binds hid-generic to it at boot:

lsusb 
Bus 008 Device 002: ID 2022:0522 DINK_HID_DEVICE DINK_HID_DEVICE

“DINK” is the display controller vendor, not Antec; the same module is in the Antec Flux Pro and a few other cases.

lsusb -v -d 2022:0522 (abridged) 
bcdUSB               1.01
bDeviceClass            0
iSerial                 3 2015-03-21
  Interface Descriptor:
    bInterfaceClass       3 Human Interface Device
    bInterfaceSubClass    0
    bNumEndpoints         2
  Endpoint Descriptor:
    bEndpointAddress   0x81  EP 1 IN     Interrupt   64 bytes
  Endpoint Descriptor:
    bEndpointAddress   0x02  EP 2 OUT    Interrupt   64 bytes

Two interrupt endpoints, 64 bytes each; you only use the OUT one. There is no handshake or initialisation sequence: the device is ready as soon as it enumerates.

Nothing here is fragile

The worst outcome of a malformed packet is a garbled or frozen readout, fixed by sending a correct packet or replugging the header; there is no writable firmware to damage.

02Why hidraw, and not libusb

Search for “USB HID from Go” or “USB HID from Rust” and the results point at libusb bindings — gousb, rusb, hidapi, pyusb — and several existing Antec projects on GitHub are built that way.

The kernel has already claimed the device with hid-generic, so libusb must first detach the kernel driver from the interface. That costs a C toolchain and libusb/libudev headers at build time, and root at runtime.

Meanwhile the kernel is already exposing the device as a character device you can open and write to like any other file:

shell 
$ ls -l /dev/hidraw0
crw------- 1 root root 243, 0 Aug  6 21:42 /dev/hidraw0

If the kernel gives you a file, use the file; that is why both implementations have no dependencies.

03Reading the report descriptor

Two facts about the write path — the report is 64 bytes, and the write starts with a zero byte — come from the device's HID report descriptor, readable as any user:

shell 
$ hexdump -C /sys/class/hidraw/hidraw0/device/report_descriptor
00000000  06 a0 ff 09 01 a1 01 09  02 a1 00 06 a1 ff 09 03
00000010  09 04 15 80 25 7f 35 00  45 ff 75 08 95 40 81 02
00000020  09 05 09 06 15 80 25 7f  35 00 45 ff 75 08 95 40
00000030  81 02 09 05 09 06 15 80  25 7f 35 00 45 ff 75 08
00000040  95 40 91 02 c0 c0

HID descriptors are a flat stream of items, each a one-byte tag followed by its data. Decoded, with the relevant items in bold:

BytesItemMeaning
06 A0 FFUsage PageVendor-defined 0xFFA0 — no standard semantics, so no kernel driver will try to interpret the reports as a keyboard or mouse
09 01 / A1 01Usage, CollectionApplication collection opens
09 02 / A1 00Usage, CollectionPhysical collection opens
75 08Report Size8 bits per field
95 40Report Count64 fields — so 64 × 8 bits = 64 bytes per report
81 02InputAn IN report, device → host. Appears twice. You never read these.
91 02OutputAn OUT report, host → device. This is the one you write.
C0 C0End Collection ×2Done
Where the zero byte comes from

There is no 0x85 (Report ID) item in those 70 bytes: this device declares no report IDs.

The hidraw write interface always treats the first byte of your buffer as a report ID. When a device has none, the kernel requires that byte to be 0x00 and strips it before the report goes on the wire. So a 12-byte packet becomes a 13-byte write().

Digits are values, not characters

44.3 °C encodes as 0x04 0x04 0x03, not '4' '4' '3' (0x34 0x34 0x33).

Blanking

Sending 0xEE 0xEE 0xEE in place of a digit triple blanks that half of the panel to --.-. Useful in three situations: a sensor you could not find, a reading that failed this tick, and shutdown — so the panel is not left showing a stale number after your process exits.

Two test vectors

Every checkpoint in both tutorials uses these:

known-good packets 
44.3 °C / 42.0 °C   ->  55 AA 01 01 06  04 04 03  04 02 00  18
blank   / blank     ->  55 AA 01 01 06  EE EE EE  EE EE EE  9B
Gotcha · the checksum overflows immediately

0x55 + 0xAA + 0x01 = 0x100. The accumulator exceeds a single byte on the third byte of every packet, before any temperature data is involved.

This has opposite consequences in the two languages: Go wraps silently and gives you the right answer; Rust panics in a debug build and wraps correctly in a release build, which presents as “my program only crashes when I'm developing”. Accumulate in a wider integer type and narrow once at the end.

What is not in the protocol

The packet always carries both temperatures. The button on your top I/O chooses which one the panel shows; your program cannot read or set that. There is no brightness, colour or text control, and no acknowledgement. iUnity's richer layouts use a second, undocumented protocol.

05Two rules for writing

Rule one — prefix the report ID byte

Your buffer is 13 bytes: a 0x00, then the 12-byte packet. Section 03 explains why. Without it the display receives the packet shifted by one byte, fails its header check, and shows nothing.

Rule two — one buffer, one write() syscall

hidraw maps each write() syscall onto exactly one HID report. Two syscalls are two reports, both malformed, so buffered writers are harmful here.

Reaching for the wrong tool

bufio.Writer in Go, BufWriter in Rust, fmt.Fprintf or write!() called once per field — all of these can split your report across syscalls or hold it until an explicit flush. Build the whole 13-byte buffer in memory, then hand it to a single write_all/Write call.

How to prove you got it right

strace -e trace=write ./your-program should show exactly one write(3, ..., 13) = 13 per second. The syscall is better proof than the right number on the panel: a torn report can still occasionally look correct.

06Warm-up: light up the panel with no code at all

Do this before writing any Go or Rust.

Send the 44.3/42.0 test vector, with its leading zero:

shell 
printf '\x00\x55\xaa\x01\x01\x06\x04\x04\x03\x04\x02\x00\x18' \
  | sudo dd of=/dev/hidraw0 bs=13 count=1

bs=13 count=1 makes dd issue a single 13-byte write. The panel should read 44.3, and keep reading it until something else writes to it. Blank it with the second vector:

shell 
printf '\x00\x55\xaa\x01\x01\x06\xee\xee\xee\xee\xee\xee\x9b' \
  | sudo dd of=/dev/hidraw0 bs=13 count=1

If the panel lit up, the device, the node and your permissions all work, so any later failure is in your code. If it did not, check that the node is yours (section 10) and that you used sudo; /dev/hidraw0 is root-only until you install the udev rule (section 09).

07Reading temperatures

Linux exposes temperature sensors under /sys/class/hwmon/ as small text files, including AMD GPU temperatures, so no ROCm or lm_sensors is needed.

shell 
$ for d in /sys/class/hwmon/hwmon*; do echo "$d  $(cat $d/name)"; done
/sys/class/hwmon/hwmon0  nvme
/sys/class/hwmon/hwmon1  nvme
/sys/class/hwmon/hwmon10  ath12k_hwmon
/sys/class/hwmon/hwmon2  amdgpu
/sys/class/hwmon/hwmon3  amdgpu
/sys/class/hwmon/hwmon4  prom21_xhci
/sys/class/hwmon/hwmon5  prom21_xhci
/sys/class/hwmon/hwmon6  k10temp
/sys/class/hwmon/hwmon7  r8169_0_900:00
/sys/class/hwmon/hwmon8  spd5118
/sys/class/hwmon/hwmon9  spd5118

Inside each directory: a name file holding the driver name, one or more tempN_input files holding millidegrees Celsius as text, and optionally a matching tempN_label naming the sensor.

shell 
$ cat /sys/class/hwmon/hwmon6/name
k10temp
$ cat /sys/class/hwmon/hwmon6/temp1_input
47125
$ cat /sys/class/hwmon/hwmon6/temp1_label
Tctl

So 47125 is 47.1 °C. Four things about these files matter in both tutorials:

Gotcha · everything ends in a newline

The files contain k10temp\n and 47125\n — verified with od -c. Parsing "47125\n" as an integer fails in both languages, with an error message that says nothing about whitespace. Worse, comparing "k10temp\n" against "k10temp" fails silently: no sensors found, no error.

Trim every sysfs read immediately.

Gotcha · the numbering has holes

k10temp on this machine exposes temp1, temp3 and temp4. There is no temp2. Any loop of the form for i in 1..=count will either miss sensors or try to read files that do not exist. Enumerate the directory; never count.

Gotcha · labels are optional

spd5118, r8169 and ath12k_hwmon have no tempN_label files. A missing label is normal — model it as an optional value, and never let its absence abort a scan.

Gotcha · every entry is a symlink

/sys/class/hwmon/hwmon6 is a symlink into the real device tree under /sys/devices/…, and so is every entry under /sys/class/hidraw/. Directory-iteration APIs in both Go and Rust report the type of the link, not its target, so a filter like “only directories” matches nothing: an empty result and no error.

One more: hwmon numbering follows driver-probe order and changes between boots. Both tutorials hardcode a path in step 2 and replace it with a scan in step 3.

The two-amdgpu problem

A Ryzen desktop chip with integrated graphics plus a discrete card gives you two amdgpu hwmon instances, and the wrong one shows the iGPU's idle temperature. On this machine:

PathInputsLabelsWhich
hwmon2temp1, temp2, temp3edge, junction, memDiscrete RX 9070 — what you want
hwmon3temp1edgeGranite Ridge iGPU

A discrete card reports edge, junction and memory; an integrated one reports only edge. Pick the instance with the most temperature inputs, and log the choice at startup so a wrong pick is diagnosable.

Design note · a missing sensor is not an error

If you cannot find a GPU, do not abort. Send 0xEE 0xEE 0xEE for that half and keep going — half a working panel beats a service that refuses to start. The same applies to a read that fails on one tick: blank it, log it, carry on.

09Permissions

/dev/hidraw0 is crw------- root root. Three options, best first:

A udev rule, so your normal user can write to the node while developing. uaccess hands the device to whoever is logged in at the local seat, which is the same mechanism your webcam and joystick use:

/etc/udev/rules.d/70-antec-display.rules 
KERNEL=="hidraw*", ATTRS{idVendor}=="2022", ATTRS{idProduct}=="0522", \
  TAG+="uaccess", MODE="0660", GROUP="input"
shell 
sudo udevadm control --reload-rules
sudo udevadm trigger --subsystem-match=hidraw
ls -l /dev/hidraw0    # should now show your user via an ACL: crw-rw----+

Run as root under systemd. This is what the shipped Python service does: it reads a few sysfs files and writes one device node, and the unit file locks down everything else.

sudo ./your-program while developing. Works; install the udev rule instead.

Gotcha · permission errors look like bugs

A permission error on the device means the udev rule is missing, not that your open flags are wrong. Check ls -l first.

10Debugging toolkit

Six commands cover every problem you are likely to hit.

CommandAnswers
grep -l 0003:00002022:00000522 /sys/class/hidraw/*/device/ueventWhich hidraw node is mine? Your discovery code must agree with this.
hexdump -C out.binDid I build the bytes I think I built? Write to a scratch file instead of the device and look.
wc -c out.binExactly 13? 0 means an unflushed buffer; 14 means a stray newline.
strace -e trace=write ./progOne write(3, ..., 13) = 13 per tick, or did my report get torn in two?
watch -n1 sensorsIs the number on the panel the number the kernel reports?
journalctl -u antec-display -fWhat did the service say? Plain stdout/stderr lands here with no logging library.

The uevent file is what discovery code searches:

shell 
$ cat /sys/class/hidraw/hidraw0/device/uevent
DRIVER=hid-generic
HID_ID=0003:00002022:00000522
HID_NAME=DINK_HID_DEVICE DINK_HID_DEVICE
HID_PHYS=usb-0000:13:00.0-7/input0
HID_UNIQ=2015-03-21
Gotcha · the ID fields are zero-padded to eight digits

HID_ID is bus:vendor:product, and the vendor and product fields are padded to eight hex digits — not four. Searching for "2022:0522" matches nothing. You want ":00002022:00000522".

This exact bug shipped in the first draft of the Python version in this repo.

There are fourteen hidraw nodes on this machine, including three identical Logitech receivers and three identical DOIO keyboards; scan for your device by ID.

11What you're building

Both tutorials build the same program in the same order, so you can read one against the other.

The program has three phases: discover the device and the sensors at startup, loop (read, encode, write, sleep), and shut down cleanly. The tutorials build it from the inside out, starting with the encoding logic, which needs no I/O or hardware.

#StepWhy it's here
1The packet builderPure functions, fully testable against the two vectors, no device needed
2Read one temperatureHardcoded path. First file I/O, first error handling
3Find the sensorsDirectory scanning; the symlink and newline traps land here
4Pick the right GPUSmall, verifiable, and where iterator chains fit
5Find the device, write to itFirst light from your own code
6The loopNow it's a program rather than a script
7Survive a replugReopen on error instead of dying; keeps state, so it introduces a struct
8Graceful shutdownBlank the panel on the way out. Where Go and Rust diverge hardest
9Ship itRelease build, udev rule, systemd unit, survives a reboot

Design decisions

  • Clamp before you encode. A three-digit temperature has nowhere to go in a three-digit field. Clamp to 0–99.9 °C; narrowing casts behave differently for floats and integers in both languages.
  • Keep the file descriptor open. Open once, reopen only on error; reopening every second hides the unplug case instead of handling it.
  • Do not assume the node number survives a replug. On reconnect, re-run discovery rather than reopening the same path.
  • Test against a file, not the device. Point your writer at /tmp/panel.bin and hexdump it. Steps 1 through 5 can be verified with no device access and no root.
