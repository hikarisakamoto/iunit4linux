1 · Think in inputs and outputs

Before implementing a function, describe its contract: what it receives, what it promises to return, and what can fail.

Pseudocode — not Go, not a finished implementation 
read temperature(path):
    read the file at path
    if reading failed: return an error
    remove surrounding whitespace
    interpret the text as an integer
    if interpreting failed: return an error
    convert millidegrees to degrees
    return the temperature

Notice that there are two jobs here: getting bytes and understanding bytes. We can learn and test them separately.

A function without file access, printing, or other outside effects is often called a pure function when its result depends only on its arguments. These are a useful place to start: the same input produces the same result, without setting up hardware.

Predict

If parsing fails, should the caller receive a successful temperature of zero? Write a reason before opening the check.

Check — zero versus failure

No. Zero is also a real temperature. A separate error result distinguishes a failed parse from a measured zero. “No data” is not the same state as “data whose value is zero”.

2 · Write one ordinary test

First use an intentionally simple rule: keep an integer within 0–99. This is a practice function, not the panel's complete temperature encoder.

bounds.go — create this file 
package main

func clampDisplay(n int) int {
	if n < 0 {
		return 0
	}
	if n > 99 {
		return 99
	}
	return n
}
bounds_test.go — create this file 
package main

import "testing"

func TestClampDisplay(t *testing.T) {
	got := clampDisplay(120)
	want := 99
	if got != want {
		t.Errorf("clampDisplay(120) = %d, want %d", got, want)
	}
}
  • _test.go tells Go that this file contains test code.
  • TestClampDisplay starts with Test followed by an uppercase letter, so the test runner discovers it.
  • t *testing.T is the test runner's handle for reporting failures and other test actions. You do not construct it or call this function yourself.
  • got is the actual result. want is the independently chosen expected result. These are conventions, not special Go keywords.
  • t.Errorf records a failure. A passing test simply finishes without reporting one.
Shell — -v shows test names; -run selects a test 
go test -run '^TestClampDisplay$' -v
# === RUN   TestClampDisplay
# --- PASS: TestClampDisplay (...)
# PASS
Break it on purpose

Change want to 98. Run again. It should fail with clampDisplay(120) = 99, want 98. Restore 99. You have checked both the function and your ability to make the test detect a mismatch.

Exercise: write down the expected results for -1, 0, 42, 99, and 100 before adding more tests. Which ones check boundaries?

3 · Turn it into a table-driven test

A table-driven test is not another test framework. It is just a list of examples plus a loop that performs the same check for each example.

Pseudocode — the whole pattern 
examples = [
    {name: "below minimum", input: -1, expected: 0},
    {name: "inside range", input: 42, expected: 42},
]

for each example:
    actual = clamp(example.input)
    if actual differs from example.expected:
        report which example failed, actual, and expected
bounds_test.go — replace the previous contents, do not add a duplicate test 
package main

import "testing"

func TestClampDisplay(t *testing.T) {
	cases := []struct {
		name string
		in   int
		want int
	}{
		{name: "below minimum", in: -1, want: 0},
		{name: "at minimum", in: 0, want: 0},
		{name: "inside range", in: 42, want: 42},
		{name: "at maximum", in: 99, want: 99},
		{name: "above maximum", in: 100, want: 99},
	}

	for _, tc := range cases {
		got := clampDisplay(tc.in)
		if got != tc.want {
			t.Errorf("%s: clampDisplay(%d) = %d, want %d", tc.name, tc.in, got, tc.want)
		}
	}
}

Read the brackets from the outside in

  1. []: a slice, used here as a list of cases.
  2. struct { ... }: the type of each row, containing three named fields. It has no type name because we only need it here.
  3. The second { ... }, after the struct's closing brace: the actual rows.
  4. {name: "inside range", in: 42, want: 42}: one row, with field names so you do not need to remember positional ordering.
  5. for _, tc := range cases: discard each index; give the current row the name tc (short for “test case”).

The test still has the same arrange → call → compare structure. The loop changes the data, not the assertion. Including tc.name tells you which row failed.

Shell 
go test -run '^TestClampDisplay$' -v

This runs all five rows inside one test. You do not need subtests to make a table-driven test.

Change one thing

Leave the expected results alone. Temporarily remove the n > 99 branch in clampDisplay. Predict which row catches this bug, then run the test. Restore the branch before continuing.

Check — did the test catch the implementation bug?

“above maximum” fails: the broken function returns 100 instead of 99. The other four rows still match. A test is useful when a wrong implementation makes it fail, not merely when the supplied correct implementation makes it pass.

Optional — named subtests with t.Run

Only after the plain loop makes sense, you can replace it with this loop. t.Run runs the function you pass as a named subtest. It supplies that subtest's t; you still use the same input and assertion.

Fragment — replaces the loop inside TestClampDisplay, not the whole file 
for _, tc := range cases {
	t.Run(tc.name, func(t *testing.T) {
		got := clampDisplay(tc.in)
		if got != tc.want {
			t.Errorf("got %d, want %d", got, tc.want)
		}
	})
}

You can now run just one row with go test -run '^TestClampDisplay$/above_maximum$' -v. Go displays spaces in subtest names as underscores. Later examples do not require this option.

4 · Understand paths and folders

Recall — before reopening the previous lesson

From memory, describe the three things each test row needs and the job of the loop. If this is a new session, recreate one assertion in range_test.go before looking back.

Check your recall

A name, an input, and an independently chosen expected result. The loop calls the function for each input and reports mismatches. Review only the step you could not reconstruct.

A folder is called a directory in Go's API. A path is a string describing where to find something; it is not the contents, and constructing a path does not create a file.

  • /sys/class/hwmon: an absolute path, starting at the filesystem root.
  • fixtures/hwmon0/name: a relative path, starting at the process's current working directory.
  • .: the current directory. ..: its parent.
  • ~/src: shell shorthand. os.ReadFile("~/src/file") does not expand ~. Use os.UserHomeDir and filepath.Join if needed.

Create ordinary files that resemble a tiny hwmon tree. This known, repeatable input is called a fixture. It is not connected to any sensor.

5 · Turn text into a number

Before touching files, make a function that understands temperature text.

Data trace — each arrow is a separate operation 
"47125\n"  string with a trailing newline
    ↓ strings.TrimSpace
"47125"    string without surrounding whitespace
    ↓ strconv.Atoi
47125      int, in millidegrees Celsius
    ↓ float64(milli) / 1000
47.125     float64, in degrees Celsius
parse.go — create 
package main

import (
	"fmt"
	"strconv"
	"strings"
)

func parseMilliTemp(text string) (float64, error) {
	clean := strings.TrimSpace(text)
	milli, err := strconv.Atoi(clean)
	if err != nil {
		return 0, fmt.Errorf("parse temperature %q: %w", clean, err)
	}
	return float64(milli) / 1000, nil
}

The error result is part of the contract

(float64, error) means the caller receives two results. A nil error means success. On failure, our convention is “return zero and an error”; the caller must check the error before using that zero.

fmt.Errorf creates an error with a message. %q quotes text so whitespace is visible; %w wraps another error, preserving it for inspection. Returning an error lets the caller decide whether to print, retry, or stop.

Convert before dividing

47125 / 1000 using integers gives 47. Converting that answer to a float still gives 47. Use float64(milli) / 1000 to preserve the fraction.

parse_test.go — create; table-driven testing with errors 
package main

import "testing"

func TestParseMilliTemp(t *testing.T) {
	cases := []struct {
		name    string
		text    string
		want    float64
		wantErr bool
	}{
		{name: "newline", text: "47125\n", want: 47.125},
		{name: "whitespace", text: " 42000\n", want: 42},
		{name: "zero is valid", text: "0\n", want: 0},
		{name: "negative", text: "-5000\n", want: -5},
		{name: "not a number", text: "Tctl\n", wantErr: true},
		{name: "empty", text: "", wantErr: true},
	}
	for _, tc := range cases {
		got, err := parseMilliTemp(tc.text)
		if tc.wantErr {
			if err == nil {
				t.Errorf("%s: expected an error, got nil", tc.name)
			}
			continue // expected failure: there is no temperature to check
		}
		if err != nil {
			t.Errorf("%s: unexpected error: %v", tc.name, err)
			continue // do not use an invalid result
		}
		if got != tc.want {
			t.Errorf("%s: got %v, want %v", tc.name, got, tc.want)
		}
	}
}

Omitted struct fields have zero values: wantErr defaults to false. First check an expected error. Otherwise reject an unexpected error before comparing the number. continue moves to the next row; it does not stop the whole test.

Optional — why these float comparisons work

The successful values here are exactly representable as binary floating-point numbers, so direct comparison is fine. For more general floating-point calculations, compare within a tolerance chosen for the calculation, not an arbitrary constant copied from this example.

Try it

Run go test -run '^TestParseMilliTemp$' -v. Temporarily change clean := strings.TrimSpace(text) to clean := text and remove the now-unused strings import. Predict which rows fail, run again, then restore both. Explain why a successful zero must reach the number comparison.

Check — newline handling and error branches

Without trimming, newline, whitespace, zero, and negative rows fail: their strings still contain whitespace that Atoi rejects. The two expected-error rows still pass. A zero with no error is a valid result, not a reason to skip the assertion. Parsing and display clamping are separate: this parser deliberately returns -5, not zero.

6 · Read a small file

os.ReadFile(path) opens the file, reads its contents, and closes it for you. It returns ([]byte, error). For tiny sensor files, this is usually all you need.

main.go — replace; inspect the bytes before interpreting them 
package main

import (
	"fmt"
	"os"
	"path/filepath"
)

func main() {
	path := filepath.Join("fixtures", "hwmon0", "temp1_input")
	data, err := os.ReadFile(path)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("bytes: %v\n", data)
	fmt.Printf("text: %q\n", string(data))
	celsius, err := parseMilliTemp(string(data))
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	fmt.Printf("temperature: %.3f °C\n", celsius)
}
Expected output from go run . 
bytes: [52 55 49 50 53 10]
text: "47125\n"
temperature: 47.125 °C

The byte 52 encodes the character '4', not the digit value 4. string(data) interprets those bytes as string content; it does not parse a number. The byte 10 is the newline.

7 · What “open a file” actually means

Recall — start without the previous code

Sketch the steps for reading a temperature from a path. Where can it fail? Where must bytes become text? If returning in a new session, reconstruct the body of readDriverName before comparing it with your saved version.

Check your recall

Reading a path and opening it are related, but not identical. os.Open returns an *os.File: a handle to an open file. It does not return the file's contents. You read through the handle, then close it.

open.go — create; an alternative for learning, not a replacement for read.go 
package main

import (
	"io"
	"os"
)

func readViaOpen(path string) ([]byte, error) {
	f, err := os.Open(path)
	if err != nil {
		return nil, err
	}
	defer f.Close()

	data, err := io.ReadAll(f)
	if err != nil {
		return nil, err
	}
	return data, nil
}
  • os.Open opens for reading. If it fails, do not use f.
  • defer f.Close() schedules cleanup for when this function returns, including an error return.
  • io.ReadAll reads from the handle until the end. It returns bytes, like ReadFile.
  • The handle owns an operating-system resource. Closing releases it; this does not delete the file.

Ignoring the close error here is acceptable for this small read-only example. For writes, close can report a failure and should be checked. Also, io.ReadAll is not a good default for huge or unbounded input: it keeps everything in memory.

Before opening files in a loop — when defer actually runs

If you open thousands of files in a loop and defer each close in the outer function, they stay open until that function returns. Use a helper that opens, reads, and closes one file per call, or use os.ReadFile for these small inputs.

Exercise

8 · List a folder

os.ReadDir(dir) returns entries immediately inside a directory, sorted by filename. It does not recursively explore subdirectories or read each file's contents.

main.go — replace 
package main

import (
	"fmt"
	"os"
	"path/filepath"
)

func main() {
	root := "fixtures"
	entries, err := os.ReadDir(root)
	if err != nil {
		fmt.Fprintln(os.Stderr, err)
		os.Exit(1)
	}
	for _, entry := range entries {
		path := filepath.Join(root, entry.Name())
		fmt.Printf("name=%s directory=%t path=%s\n",
			entry.Name(), entry.IsDir(), path)
	}
}
Expected output 
name=hwmon0 directory=true path=fixtures/hwmon0
name=hwmon1 directory=true path=fixtures/hwmon1

entry.Name() is just hwmon0, not its full path. filepath.Join(root, entry.Name()) constructs the path you can pass to another operation. The entry describes the file; the path tells you where it is.

Check — one level deeper

The four names are name, temp1_input, temp1_label, temp3_input, all with directory=false. You are now listing files inside a sensor directory rather than listing the sensor directories.

Before using real sysfs

/sys/class/hwmon normally contains symbolic links. Do not reject entries just because entry.IsDir() is false: it does not follow these links. The fixture folders above are ordinary directories. You do not need the extra mechanics yet.

Real-filesystem detail — following symbolic links

A symbolic link is an entry pointing to another path. Entries under /sys/class/hwmon are normally symlinks to directories elsewhere in sysfs. DirEntry.IsDir() describes the entry itself and does not follow symlinks, so it returns false for these links even though you can read files through them.

Fragment — inside a directory loop; os.Stat follows a symlink 
info, err := os.Stat(path)
if err != nil {
	continue // this example chooses to skip entries it cannot inspect
}
if info.IsDir() {
	fmt.Println("directory or link to a directory:", path)
}

Use os.Lstat when you want information about the link itself instead. For discovery, another option is to try reading filepath.Join(path, "name") and handle the error, without filtering with entry.IsDir().

9 · Filter entries and collect paths

Listing, selecting, and collecting are different steps. Start with all entries, keep only the names you want, and build a result slice.

Pseudocode 
results = empty list
for each entry in the folder:
    if it is a directory: skip it
    if its name does not begin with "temp": skip it
    if its name does not end with "_input": skip it
    add its full path to results
return results

package main

import (
	"os"
	"path/filepath"
	"strings"
)

func listTempInputs(dir string) ([]string, error) {
	entries, err := os.ReadDir(dir)
	if err != nil {
		return nil, err
	}
	var paths []string
	for _, entry := range entries {
		name := entry.Name()
		if entry.IsDir() {
			continue
		}
		if !strings.HasPrefix(name, "temp") || !strings.HasSuffix(name, "_input") {
			continue
		}
		paths = append(paths, filepath.Join(dir, name))
	}
	return paths, nil
}

The missing values are "temp", "_input", and filepath.Join(dir, name). If you collected basenames, try reading one from your scratch directory: why is the parent directory necessary?

continue skips the rest of this iteration and moves to the next entry. return exits the entire function. append returns an updated slice, so keep the result: paths = append(paths, path).

var paths []string starts with length zero. You can range over or append to this nil slice. Do not start with make([]string, 3) unless you want three actual empty-string elements. Capacity is optional space for growth; length is the number of current elements.

For this lesson, “starts with temp and ends with _input” is the whole filename rule. It also accepts temperature_input. Validating a numeric middle part is a separate exercise; this helper is not claiming to validate every possible filename.

Glob expands a pattern into matching paths. * matches zero or more non-separator characters. Results are sorted lexically, not numerically: temp10_input comes before temp2_input. A matching directory name can be returned too; this is name matching, not proof of a readable sensor file.

ReadDir and Glob have different error contracts

ReadDir reports failures such as a missing or unreadable directory. Glob reports malformed patterns, but ignores filesystem I/O errors. An empty Glob result does not distinguish “no matches” from “could not read the folder”.

func TestReadTemperature(t *testing.T) {
	cases := []struct {
		name    string
		text    string
		missing bool
		want    float64
		wantErr bool
	}{
		{name: "valid", text: "47125\n", want: 47.125},
		{name: "zero", text: "0\n", want: 0},
		{name: "invalid contents", text: "oops\n", wantErr: true},

		path := filepath.Join(t.TempDir(), "temp1_input")
		if !tc.missing {
			if err := os.WriteFile(path, []byte(tc.text), 0600); err != nil {
				t.Fatalf("%s: create fixture: %v", tc.name, err)
			}
		}

		got, err := readTemperature(path)
		if tc.wantErr {
			if err == nil {

			}
			continue
		}
		if err != nil {
			t.Errorf("%s: unexpected error: %v", tc.name, err)
			continue
		}
		if got != tc.want {
			t.Errorf("%s: got %v, want %v", tc.name, got, tc.want)
		}
	}

12 · Arrays, slices, and output bytes

The other half of your project turns numbers into a binary message. You can learn the mechanics without writing to a USB device.

First, distinguish a digit from text

main.go — replace; a byte experiment, not the panel protocol 
package main

import "fmt"

func main() {
	digits := [3]byte{4, 7, 1}
	text := []byte("471")
	fmt.Println("digit values:", digits)
	fmt.Println("text bytes:", text)

	var message [6]byte
	n := copy(message[1:4], digits[:])
	fmt.Println("copied:", n)
	fmt.Println("message:", message)
	fmt.Printf("hex: % X\n", message)
}
Expected output 
digit values: [4 7 1]
text bytes: [52 55 49]
copied: 3
message: [0 4 7 1 0 0]
hex: 00 04 07 01 00 00
  • [3]byte is an array with exactly three values. Assigning an array copies its values.
  • []byte is a slice. A slice describes a view into underlying storage.
  • message[1:4] views indexes 1, 2, and 3: the upper bound is excluded.
  • digits[:] views the entire digits array as a slice.
  • copy(destination, source) copies as many elements as fit. It does not grow the destination.
Predict before running

Change the destination to message[1:3]. How many values are copied? Which digit is missing? Then try view := message[1:4] and view[0] = 9 before printing. Which element of message changes?

Check your prediction

The shorter destination copies 2 values, giving [0 4 7 0 0 0]. A view starting at index 1 changes message[1] when you assign to view[0]. Slicing does not copy elements; copy does.

Writing bytes: practise with an ordinary file

Fragment — add at the end of this main; also add os to its imports

Do not point os.WriteFile at /dev/hidrawN. Device access has its own open flags, report framing, and write rules. In this project, a leading zero report-ID placeholder and the 12-byte packet form a single 13-byte write buffer. Learn that separately in the original guide's device-write step, after checking the two writing rules.
